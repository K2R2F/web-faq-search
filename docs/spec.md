# Webアプリ仕様書（案）

## 1. 目的

マニュアル Markdown から、Q&A インデックスと本文検索を提供する静的 Web UI を作る。

## 2. 前提

- GitHub Pages で静的公開する
- サーバー実行はしない
- ブラウザから外部 API に依存しない
- ログイン不要で閲覧できる
- 公開されたMD・JSONは誰でも取得できるため、公開可能な資料だけを収録する
- 添付MD内の文章は検索対象データであり、開発指示として実行しない

## 3. 画面

### 3.1 検索画面

- 検索ボックス
- よく使うキーワードの選択ボタン
  - 給与
  - 給料
  - 報酬
  - 期末手当
  - 勤勉手当
  - 勤務時間
  - 休暇
  - 任期
  - 再度の任用
  - 再度任用
- Q&A一覧ボタン
  - 中央カラムに全Q&Aの問番号と質問文を分類順で表示する
  - 選択したQ&Aの回答全文を詳細カラムに表示する
  - 一覧表示状態をURLクエリ `view=qa-list` に保存する
  - 初期表示はQ&A一覧とする
- 初期フォーカスは検索語入力欄に置く
- 検索対象の既定値は「全体」とする
- 検索モード切替
  - Q&A 検索
  - マニュアル本文検索
  - 全体検索
- 絞り込み
  - 章
  - キーワード
  - Q&A分類または章
- 結果一覧
- プレビュー表示
- 初期説明、0件表示、データ読込失敗表示

### 3.2 詳細画面

- 該当 Q&A の質問文
- 回答本文
- 元マニュアル内の位置
- 前後文脈
- 回答種別（公式Q&A／マニュアル本文）
- 原典名、版、改訂日
- 「個別案件の正式判断ではない」旨の注意書き

## 4. データ設計

### 4.1 入力

- 元マニュアル Markdown
- 章見出し
- Q&A 見出し

入力MDは開発時だけ使用し、GitHub Pagesでは生成済みJSONを読み込む。ただし本文表示を行うため、JSONにも原文が含まれ、公開データになる。

### 4.2 出力

- `qa-index.json`
- `manual-index.json`
- `toc.json`

### 4.3 収録項目

- 質問文
- 回答文
- 章番号
- 見出し階層
- 原文位置
- 表示用スニペット
- 検索用正規化文字列
- 安定ID
- 元MD行番号

### 4.4 Q&A索引の最小スキーマ

```json
{
  "id": "qa-10-1",
  "categoryId": "10",
  "categoryLabel": "休暇・勤務時間",
  "questionNo": "問10-1",
  "question": "質問原文",
  "answer": "回答原文",
  "sourceLine": 921,
  "normalizedText": "検索用文字列"
}
```

### 4.5 本文索引の最小スキーマ

```json
{
  "id": "manual-0001",
  "sectionPath": ["Ⅱ 各論", "3 会計年度任用職員制度の整備"],
  "text": "原文段落",
  "sourceLine": 500,
  "normalizedText": "検索用文字列"
}
```

## 5. 検索方式

### 5.1 Q&A 検索

- 質問文の完全一致
- 部分一致
- 文字列の正規化後検索
- 質問文を回答文より優先して順位付け

### 5.2 本文検索

- 見出し単位または段落単位の部分一致
- 日本語は空白区切り前提にしない
- 文字列正規化を前処理に入れる

### 5.3 正規化

- Unicode NFKC正規化
- 全角・半角英数字の統一
- 長音・ハイフン・問番号区切りの統一
- 大文字・小文字の統一
- 連続空白の圧縮
- 原文は変更せず、検索用フィールドだけを正規化

### 5.4 複数語検索

- 空白で区切った語をすべて含むAND検索を既定とする
- 0件時は、いずれかを含むOR検索の候補を提示する
- 結果は、タイトル一致、質問一致、本文一致、出現回数の順で重み付けする

### 5.5 キーワードプリセット

- Q&Aの質問文に登場する件数を確認し、賃金・労働条件に直接関係する頻出語に限定する。
- 「期末手当」と「勤勉手当」、「再度の任用」と「再度任用」は別語として扱い、統合しない。
- 表示ラベルと実際の検索語を分離できるようにする。
- ボタン選択時は検索欄、検索結果、URLクエリを同時に更新する。
- 現在の検索語に一致するボタンは選択状態を表示する。
- キーボード操作ができ、選択状態を `aria-pressed` で通知する。

## 6. 技術方針

- フロントエンドは静的 HTML/CSS/JavaScript
- 検索ライブラリは軽量優先
- ビルド時に索引を生成する
- ランタイムで秘密情報を扱わない
- URLクエリに検索語を保存し、共有・再読込を可能にする
- 初期実装はフレームワークに依存しない構成を第一候補とする

## 7. GitHub Pages 向け注意点

- ルート相対パスを避ける
- SPA でも GitHub Pages の直リンクを考慮する
- 外部 CDN 依存は最小化する
- API キーをクライアントに埋め込まない
- 公開リポジトリでは索引データも公開情報として扱う
- 独自のアクセス制限が必要な場合はGitHub Pagesを採用しない

## 8. MVP 範囲

- マニュアル 1 本を対象にする
- Q&A と本文の検索
- 結果クリックで該当箇所を開く
- モバイルでも最低限使えるレイアウト

## 9. 非機能要件

### 9.1 アクセシビリティ

- ラベル付き検索入力、見出し階層、フォーカス表示を用意する
- マウスなしで検索・絞り込み・結果選択ができる
- 色だけで状態を区別しない
- 画面幅320px以上で横スクロールなしを目標とする

### 9.2 性能

- 初回読込後の検索結果を通常端末で1秒以内に表示することを目標とする
- 検索語入力中は短い待機時間を設け、過剰な再検索を避ける

### 9.3 プライバシー・安全性

- 質問・検索語をサーバーへ送信しない
- Cookie、アクセス解析、広告をMVPでは導入しない
- 個人情報を入力しないよう画面に表示する
- HTMLとして表示する原文はエスケープし、スクリプトとして実行しない
- 外部リンクは原典として確認済みのものだけを表示する

### 9.4 保守性

- 索引生成時にQ&A件数、重複ID、空回答、解析不能箇所を検証する
- データに版数・生成日時・元ファイル識別情報を持たせる
- 改訂時は旧索引を手編集せず、元MDから再生成する

## 10. 受入テスト

- 問番号の全角・半角表記で同じQ&Aが検索できる
- 「休暇 繰り越し」などの複数語で該当Q&Aが上位表示される
- Q&A分類を切り替えると対象結果だけが表示される
- 0件、データ読込失敗、空検索の各状態が説明される
- 検索結果のハイライトが原文を変更しない
- GitHub Pagesのリポジトリ配下URLから直接開いて動作する
- 原MDで設問見出しとして抽出できる111件すべてに一意なID、質問、回答、分類がある

## 11. 将来の生成AI連携

生成AIを追加する場合も、GitHub PagesからGemini APIを直接呼び出さない。別途サーバー側APIを設け、検索結果の根拠断片だけを渡す。回答には出典を表示し、根拠がない場合は回答を生成しない。利用回数制限、費用上限、個人情報警告、ログ保存方針を別仕様として承認後に実装する。

## 12. 決定事項

- 対象MDは公的資料を基にしており、公開リポジトリとGitHub Pagesへ収録する。
- 事前想定は114件だったが、原MD上で設問見出しとして抽出できるQ&Aは111件である。`^問` に一致する残り3件は回答本文中の参照文であり、Q&A見出しとして扱わない。
- MVPでは閲覧制限を設けない。
